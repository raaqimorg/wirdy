Cache, prefetch, and search audit

An audit of how wirdy.site caches, prefetches, and searches, on 2026-11-27, at bc7dcba (the commit that is live). Each finding below was reproduced, not inferred. Nothing here is built yet: each fix waits for your decision.

The short answer

Area Verdict Recommendation
Caching One real stale-data bug, and a design flaw that makes every content deploy drop every cached page. Fix C1 now (small). Then C2 and C3.
Prefetching Matches the goal. The main pages and search are prefetched, the inner pages are not. There are no page images to prefetch. Add intent prefetch for inner pages (P1).
Search Fast for real queries, slow on phones for one to three letters. Three content fields are not searchable, and the fallback shows hundreds of unrelated rows. S1, then Q1 to Q3.

How it was tested

  • Live headers: curl against wirdy.site. The live / is byte-identical to a local build of bc7dcba.
  • Deploys: three local builds. A is bc7dcba. B changes the CSS and the search index. C changes only the search index version (as any dhikr edit does). A small Bun server serves them with the headers Cloudflare Pages sends: the _headers rules, max-age=0, must-revalidate and no ETag on HTML, a 308 to the trailing slash, and a 404 for a removed file (all checked live). An endpoint switches the deploy, as wrangler pages deploy does.
  • Browser: Brave, headless, through playwright-core (a dev dependency already), with a persistent profile so the service worker survives.
  • Phone speed: Chrome DevTools CPU throttling at 6x on a 390 by 844 viewport, as an approximation of a low-end Android phone. Not a real device.
  • Search quality: the real match and nearestOf from src/lib/search.ts, run on the built index (285 rows) with 43 queries.

Safari was not tested: Playwright's WebKit is not installed here, and Safari cannot be driven headless. Each fix below works the same way in every browser.

1. Caching

CriticalC1. The Back button can pin an old page

The worker stores a page under its new fingerprint without checking the bytes. After a deploy, a Back or Forward navigation lets the browser answer from its HTTP cache without asking the server. The worker stores that old page under the new fingerprint. From then on, that page is old on every visit, until a later deploy changes it again.

Reproduced (with and without the back-forward cache):

  1. Deploy A. Open /, then /sabah-masaa/ayat-al-kursi/, then /nawm/.
  2. Deploy B. Open /salah/ and wait 5 s, so worker B takes over.
  3. Press Back twice, to /sabah-masaa/ayat-al-kursi/.
Server
Saw no request for that page after the deploy.
Worker cache
Key ?v=58ff3c1e9bc194f5 (the B fingerprint) holds the A page (it links SiteFooter.BYberPoT.css, which B does not have).
Later
A fresh visit in a new tab and a reload both show the A page. Search still worked only because the old CSS and index were still in the HTTP cache. Without them, the page loads with no styles and search fails, since the server answers 404.

Why it matters here: a corrected dhikr text can stay wrong on a reader's phone for weeks, which is the exact risk you named.

Fix:

  • In keep(), hash the page with crypto.subtle.digest('SHA-256') and store it only when the first 16 hex characters equal its fingerprint. On a mismatch, still show the response, but do not store it, and fetch the page again in the background with cache: 'no-cache'.
  • On activate, check the body of each kept page the same way, and delete a mismatch. This also cleans any page already pinned on readers' phones today.
  • A test in offline.test.ts for the check.

Trade-off: a SHA-256 of the largest page (217 KB, /nawm/) takes 0.08 ms on this Mac (Web Crypto in Bun). A slow phone is perhaps 10 times slower, still under 1 ms, on the worker thread. None other. About 20 lines in service-worker.js.

HighC2. Any dhikr change drops every cached page

Every page holds the versioned path of the search index (data-search-index="/search/c887c2a3345b.json"). Any change to any search row (a text, a title, a when) renames the index, so it changes the bytes, and the fingerprint, of every page.

Measured: build C changes only the index version. All 303 of 303 page fingerprints change. The docs say "A deploy drops only the pages it changed". Today that is true only for a CSS-free, content-free deploy.

What each content deploy costs (21 commits touched content in the last 30 days):

  • Every returning reader downloads the 18 main pages again: 192 KB (Brotli).
  • Every inner page the reader opened is deleted. Reproduced: offline, /sabah-masaa/ayat-al-kursi/ opened before deploy C fails with net::ERR_FAILED after it. The kept pages go from 19 to 18.

Option A (recommended): one fixed index URL.

  • Serve the index at /search/index.json with Cache-Control: no-cache. Cloudflare sends an ETag on non-HTML files and answers 304 (checked live: site.webmanifest with If-None-Match gives 304, 0 bytes).
  • The worker keeps the index under its content hash, which is already in the worker's manifest, so a reader with the worker never asks the server.
  • The pages no longer change when a dhikr changes. Only the changed pages drop.

Trade-off: a reader with no worker sends one conditional request (a 304 of a few hundred bytes) for the index on each page, 1 s after load, off the critical path. Today that request does not happen, because the versioned file is cached for a year.

Option B: keep the versioned file, leave data-search-index out of the fingerprint, and let the worker answer any /search/*.json with the current index. Zero extra requests, but it is more unusual code, and a fingerprint that ignores part of the page is easy to get wrong later.

A CSS or JavaScript change still drops every page. That is correct, because every page links them, and it is rare.

MediumC3. Offline, an unopened page shows the browser's error

Reproduced: offline, a dhikr page never opened gives net::ERR_FAILED, the browser's own error page, with no way back to the site.

Fix: keep 404.html (6 KB Brotli), or a small offline page made from it, and serve it when a navigation fails. It has the bar, search, and the home link.

Trade-off: one more page in the first prefetch.

I do not recommend serving an older copy of a page offline. For this site, an old text of a corrected dhikr is worse than a clear "not available offline".

CheckedWhat is right today

  • /_astro/*, /search/*, /offline/*, /og/*, and /opengraph/* are immutable for a year, and every one has a content hash in its name (checked in dist/).
  • The icons are cached 7 days and the pages link them with ?v=ICON_VERSION.
  • service-worker.js is no-cache with an ETag: live answers cf-cache-status: REVALIDATED.
  • HTML is max-age=0, must-revalidate, and a missing page is a 404 with no-store.
  • The build is deterministic: the live home page equals a local build byte for byte.

Tested and not a problem

An open tab during a deploy. I expected the new worker to delete the old index before the old page asked for it. It did not happen: the page asked for the index at 1041 ms, and the new worker took over at 2067 ms (one run, local server, no network delay; a real network only makes the new worker later). The old page loads all its fonts, CSS, and JavaScript at once, so nothing late is lost. No change needed.

Not tested

Safari deletes the storage of a site, the worker's caches included, after 7 days of browser use with no visit to that site. This is a WebKit policy, not a bug here. A reader who adds the site to the home screen is exempt. It only means the first visit after a long break downloads the main pages again.

2. Prefetching

What happens today (measured)

On the first visit, after load, the worker downloads these, once, then keeps them:

What Files Size (Brotli)
The home page and the 17 pages its cards open 18 192 KB
Fonts (woff2) 5 280 KB
Search module, CSS, search index 3 60 KB
Not prefetched: the inner pages 285 2.0 MB (median 7 KB)

Most of the fonts, the CSS, and the module are already in the HTTP cache from the page itself, so the new network bytes are about 250 KB (the pages, the index, and the Quran font when the first page does not use it), close to the 270 KB the docs give. This matches your goal: the main pages and search are prefetched, the inner pages are not.

Images

No page has an image to prefetch. There is no <img> in dist/. The emblems, the mark, and the icons are inline SVG (45 on the home page). The only images are the share cards, 285 of them, 57 MB in all (about 200 KB each), opened only by «الصورة» or a link preview. Prefetching them would cost a reader 57 MB. Keep them out.

A small gap: favicon.svg, icon-192.png, and site.webmanifest are not kept (9 KB). Offline, the tab has no icon. Add them to the worker's files: harmless, but cosmetic.

RecommendedP1. Prefetch an inner page when the reader reaches for it

A tap on a dhikr or a hadith goes to the network: one round trip, plus the worker's start. On a phone, a touch starts about 100 ms before the click. On a desktop, a hover starts several hundred ms before it.

Proposal: on touchstart, pointerdown, or a 65 ms hover over a same-site link to a page the worker knows, the inline script posts the path to the worker. The worker fetches it and keeps it (with the C1 check). The click then opens it from the device.

  • Size: about 12 lines in Paper.astro, 10 in the worker.
  • Cost: about 7 KB for a hover that does not end in a click. Nothing with Save-Data.
  • It needs an entry in exceptions.md.

Normal way: Speculation Rules (<script type="speculationrules">, eagerness: "moderate"). Zero JavaScript. But exceptions.md records that only Chrome uses it (Brave turns it off, Safari has none), so readers on Safari and Brave gain nothing. I recommend the worker message because it works in every browser that has the worker.

OptionalP2. Keep the next and previous dhikr

On a dhikr page, when the browser is idle, keep the two neighbours, so a reader who walks through a section never waits. 14 KB for each page opened.

Not recommendedPrefetch every inner page

2 MB for each reader, and again after each deploy that changes them.

3. Search

Speed (measured at 6x CPU throttling)

Query Rows shown Handler Keystroke to paint
ا 302 29 ms 267 ms
ال 302 47 ms 211 ms
الله 237 24 ms 143 ms
من قالها 166 17 ms 122 ms
النوم 21 6 ms 49 ms
سيد الاستغفار 2 2 ms 12 ms

The matching is fast (under 50 ms even for one letter). The cost is the browser laying out 200 to 300 visible rows. 200 ms is the upper limit of a "good" interaction in Google's INP measure.

Also measured: filling the hidden list (1,710 elements) 1 s after load drops no frame over 50 ms, so it is not a problem. Evaluating the search module costs 100 to 133 ms of main thread at first paint, on every page.

RecommendedS1. Lay out only the rows on screen

Add content-visibility: auto and a contain-intrinsic-size to a result row. CSS only, so it is the normal way. If one letter is still over 200 ms, show the first 40 rows and a «عرض كل النتائج (٢٣٧)» button.

Trade-off: the scroll bar can jump a little while rows lay out. The cap, if needed, adds one tap to see every row.

LaterS2. Load the search module on intent

Import it on the first focus, hover, or tap of the search button, or when idle, and save 100 to 133 ms on every page. The pending tap in Paper.astro already covers a tap before it loads. Measure after S1: it may not be worth the change.

Quality (the real index, 285 rows)

Query Today Why
من قالها 149 rows for «من» «قالها» is in 10 fadl fields, which are not indexed
غفرت له ذنوبه 249 rows for «له» fadl not indexed, and the fallback takes a word in every row
حسبي الله 220 rows for «الله» no dhikr has «حسبي»; the fallback shows almost the whole index
البخاري 0 the takhrij source is not indexed
صحيح مسلم 4 rows for «مسلم» (wrong ones) the takhrij source is not indexed
ابو هريرة 2 rows for «ابو» (wrong ones) the rawi is not indexed, and it is stored as «أبي»
يس 17 rows a substring inside «ليست» and others
المعوذتين 0 the rows say «المعوذات»
سيد الاستغفار، الكرب، الحبة السوداء، قبل النوم right title and text matches work well
رمضان، العيد، الرعد، الحسد، الصداع 0, correctly no dhikr or hadith has these words

RecommendedQ1. Index three more fields

Add fadl (76 adhkar), rawi (36 hadiths), and the takhrij source (all 285) to each row, ranked below the title and the text, as about is today. A reader can then find «من قالها», «البخاري», or a narrator.

Trade-off: 14.6 KB more raw text in the index (148 KB today), about 2 to 3 KB after Brotli. A source match can be noisy («مسلم» is in many sources), so the source ranks last.

RecommendedQ2. A fallback that helps

When all the words find nothing, search shows the rows of the longest word that finds something, even when that word is in almost every row («الله», «له», «من»). Instead:

  • Show the rows that match the most query words, best first.
  • Skip a word that is in more than 20% of the rows (about 57).
  • If nothing is left, say no result, and show the six suggestions.

RecommendedQ3. Short words match the start of a word

A query word of one or two letters matches only at the start of a word, after a prefix such as و، ف، ب، ل، ال. A word of three letters or more still matches anywhere, so «بالله» still finds «الله». «يس» stops matching «ليست».

OptionalQ4 to Q6

  • Q4. Synonyms: «المعوذتين» to «المعوذات», «أبو» to «أبي» (for the rawi), «الحسد» to «العين». Each must be checked against the content first, as the short list asks.
  • Q5. Sections as results: typing «السفر» shows the page «أذكار السفر» first. 18 rows more.
  • Q6. Ranking: a title that starts with the query comes first, then a title that has it, then the text.

Not recommendedTypo tolerance or a stemmer

exceptions.md records that a stemmer turned «اية الكرسي» from 3 results to 40. Fuzzy matching on Arabic roots has the same risk. Revisit only as a «هل تقصد» line when a query finds nothing.

Order of work

  1. C1, alone, in one small pull request. It is the stale-data bug.
  2. C2 (option A) and C3, in one pull request on the worker.
  3. S1, then Q1 to Q3, in one pull request on search.
  4. P1, then the optional items, if you want them.

Each change updates docs/exceptions.md in the same commit (the worker and search entries), and runs bun run ci. None needs a deploy to test: the local two-deploy setup above reproduces each case before and after.
